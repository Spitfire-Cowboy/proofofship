The problem with developer profiles

Most developer profiles are self-reported. You list your projects, describe your contributions, and people take your word for it.

There is no systematic way to ask: did this person actually build this, and can anyone verify it?

As AI-generated code becomes common, this gap gets worse. It is increasingly easy to claim work that was generated, copied, or fabricated. The signal-to-noise ratio for evaluating builders is dropping.

How proofofship works

Proof → Verify → Reputation.

A builder produces proof of shipped work. Proofofship independently verifies each claim against the public record. Verified claims accumulate into a reputation score anyone can recompute.

  1. Ship work

    A builder commits code to a public repository.

  2. Generate a receipt

    A local tool (ship-receipts) creates a proof envelope: artifact reference, actor identity, cryptographic hash.

  3. Verify independently

    Proofofship checks each claim against the GitHub API. Does the commit exist? Is the repo public? Does the actor have push access? Is the commit signed?

  4. Score and publish

    Verified receipts earn a reputation score — time-decayed, depth-weighted, and deterministic. Every input is public. Anyone can recompute any score.

No self-reported claims contribute to the score. If proofofship cannot independently verify the artifact, it earns zero reputation.

What “verified” actually means

Not all receipts are equal. Proofofship scores each one by how deeply it was verified — and shows that depth explicitly.

Verification depth

  • ░░░░░ 0.0 — Not verified
  • █░░░░ 0.2 — Schema valid
  • ██░░░ 0.4 — Artifact confirmed
  • ███░░ 0.6 — Cryptographically signed
  • ████░ 0.8 — Independently attested (planned)
  • █████ 1.0 — All stages passed (planned)

Time decay

Reputation decays. A 90-day-old receipt contributes half its original weight. A year-old receipt contributes about 6%.

What we do not verify

Proofofship verifies that artifacts exist in public repositories and that the actor has write access. It does not verify code quality, project impact, or that the actor personally authored every line. Push access proves permission, not authorship.

Two tools, one trust boundary

ship-receipts is the local tool. It runs inside a single repo, generates a proof envelope for each session of shipped work, and stores it alongside the code. It records evidence — it does not verify or score anything.

proofofship is the independent service. It accepts envelopes from any conformant source, re-verifies every claim from scratch against the public record, and publishes a reputation score.

The trust boundary is strict: proofofship never trusts scores or claims inside an envelope. All verification starts from zero.
